# BUG-003: Verbo HTTP não suportado retorna 404 em vez de 405

| Campo | Valor |
|---|---|
| Status | Aberto |
| Severidade | Baixa |
| Prioridade | Baixa |
| Encontrado em | Execução manual (roteiro), casos CT-API-01 e CT-API-02 (VADER: Verbos); confirmado na sessão EXP-API, que acrescentou `OPTIONS` |
| Condição / requisito | CND-16, CND-17 |
| Ambiente | Windows, Node.js, Git Bash, `curl`, aplicação v1.0.0 em `localhost:3000` |
| Evidência | `docs/evidencias/CT-API-01.txt` e `docs/evidencias/CT-API-02.txt` |

## Descrição
Rotas existentes chamadas com um verbo não suportado respondem 404 ("Recurso não encontrado."). Pela semântica HTTP, o código correto é 405 (Method Not Allowed), idealmente com o cabeçalho `Allow`. Para quem consome a API, o 404 sugere que a rota não existe.

## Observação sobre o critério
O requisito não define esse comportamento. O resultado esperado vem de boa prática HTTP (por isso severidade Baixa) e foi marcado no roteiro como "a confirmar". A API rejeita as requisições e **nenhum dado é alterado**.

## Passos para reproduzir
1. Fazer login e guardar o token da Ana.
2. Executar `curl -s -w "\n[status %{http_code}]\n" -X PUT localhost:3000/api/payslips -H "Authorization: Bearer <token>"`. Repetir com `DELETE` em `/api/payslips`, `POST` em `/api/payslips/latest`, `GET` em `/api/auth/login` e `OPTIONS` em `/api/payslips/latest`.

## Resultado obtido
Nos casos executados (e em `OPTIONS`, na sessão exploratória): `[status 404]` e `{"message":"Recurso não encontrado."}`.

## Resultado esperado
`[status 405]` com o cabeçalho `Allow` indicando os verbos aceitos.

## Impacto
Baixo. Não há risco de segurança nem de dados. A mensagem é menos precisa para quem integra com a API.

## Sugestão de correção
Registrar, para cada rota, um tratador `all` que responda 405 com `Allow` para os demais verbos.
