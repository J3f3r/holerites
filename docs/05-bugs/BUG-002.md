# BUG-002: JSON malformado no login retorna 500 em vez de 400

| Campo | Valor |
|---|---|
| Status | Aberto |
| Severidade | Média |
| Prioridade | Média |
| Encontrado em | Execução manual (roteiro), caso CT-API-03 (VADER: Erros) |
| Condição / requisito | CND-17 |
| Ambiente | Windows, Node.js, Git Bash, `curl`, aplicação v1.0.0 em `localhost:3000` |
| Evidência | `docs/evidencias/CT-API-03.txt` |

## Descrição
Quando o corpo da requisição de login é um JSON inválido, a API responde com erro interno do servidor (500). Um corpo inválido é um erro do cliente e deveria ser tratado como 400.

## Passos para reproduzir
1. Iniciar a aplicação com `npm start`.
2. Executar `curl -s -w "\n[status %{http_code}]\n" -X POST localhost:3000/api/auth/login -H "Content-Type: application/json" -d '{"email": "ana@empresa.com",'`.

## Resultado obtido
`[status 500]` e `{"message":"Erro interno."}`.

## Resultado esperado
`[status 400]` com mensagem clara, por exemplo "JSON inválido.", e sem detalhes internos.

## Impacto
Médio. Erros do cliente aparecem como falhas do servidor, o que distorce monitoramento e alertas, e confunde quem consome a API. Não há vazamento de dados (a mensagem é genérica) nem queda da aplicação.

## Causa provável (análise do código, a confirmar)
O `express.json()` rejeita o corpo com um erro de status 400, mas o tratador de erros final em `src/app.js` ignora `err.status` e sempre responde 500.

## Sugestão de correção
No tratador de erros, usar `err.status` quando for 4xx (ou tratar `err.type === 'entity.parse.failed'` com 400 e a mensagem "JSON inválido.").
